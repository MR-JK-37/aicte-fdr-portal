# S-03 — `expo-glass-effect` + `expo-symbols`

**Status: PASS (doc-verified) for the "is iOS 26+ real" question; fallback behavior confirmed for glass-effect, partially confirmed for symbols.**

## What was tested
1. Whether "iOS 26+" is a real, shipped requirement (not a hallucinated future version) per Apple's and Expo's own docs.
2. What `expo-glass-effect` requires and how it degrades pre-iOS-26 / under Reduce Transparency.
3. What `expo-symbols` requires and its documented fallback behavior.

## What was verified (official sources)
### iOS 26 reality check
iOS 26 is real and shipped — this is independently corroborated by the Expo SDK 58 changelog itself, which states SDK 58 "is built for **iOS 27**" (i.e., the platform generation *after* 26), and by the `expo-glass-effect` and Expo UI blog material referencing "iOS 26 Liquid Glass" features as already-shipped in SDK 54's "iOS 26 Liquid Glass icons + Expo UI" announcement. So "iOS 26+" is not a guess — it is the platform version that introduced Apple's Liquid Glass material, and as of SDK 58 the ecosystem has already moved one major version past it (iOS 27).

### `expo-glass-effect`
Per the package README (`github.com/expo/expo/blob/main/packages/expo-glass-effect/README.md`) and Expo docs (`docs.expo.dev/versions/latest/sdk/glass-effect/`):
- Provides React components rendering Apple's native `UIVisualEffectView`-based Liquid Glass.
- **`GlassView` requires iOS 26+.** On unsupported platforms/OS versions it **falls back to a regular `View`** (i.e., no glass effect, but no crash — graceful degradation is built in, not something the app must hand-roll).
- Runtime guard: `isGlassEffectAPIAvailable()` — checks at runtime whether the Liquid Glass API is actually present on-device. Documented reason: **some iOS 26 beta builds did not have the Liquid Glass API available**, which could crash apps that assumed availability from the OS version number alone. This is an important build-time note: never gate on `Platform.Version >= 26` alone — always call the runtime availability check.
- Separately, `isLiquidGlassAvailable()` checks availability in the **compiled app** (validates system + compiler version + Info.plist settings) — a build-time/compile-time distinct check from the runtime one above.

### Reduce Transparency fallback
The package's documented fallback is automatic degrade-to-`View` when the Liquid Glass API isn't available; this is the mechanism the app relies on for Reduce Transparency too, since enabling Reduce Transparency is one of the conditions where iOS itself disables the system glass material. MASTER_PROMPT §13.2 requires the product to "honour Reduce Transparency/Increased Contrast" — implementation should use the package's own availability checks rather than inferring from the accessibility setting directly, since Apple does not expose Reduce Transparency as a public runtime flag to third-party code in all cases; verify this specific interaction (package behavior under Reduce Transparency specifically, vs. just OS-version fallback) at Phase 1 against the live package test suite — the fetched docs confirm OS-version/API-availability fallback clearly, but do not explicitly confirm the Reduce-Transparency-specific code path in the text retrieved.

### `expo-symbols`
Per `docs.expo.dev/versions/latest/sdk/symbols/`:
- Renders native SF Symbols on iOS; for Android/web, the library substitutes **Material Symbols** instead of SF Symbols given a platform-specific symbol-name mapping.
- Documented fallback prop: if a string-only (SF Symbol) name is given and the symbol isn't resolvable on the current platform, **nothing renders unless a `fallback` prop (`React.ReactNode`) is supplied** — this is an explicit, documented behavior (not inferred): always pass `fallback` or a platform-keyed symbol-name object.
- Could **not** confirm the exact minimum iOS version `expo-symbols` requires from the fetched excerpt (the page didn't state it explicitly in what was retrieved) — this is a **gap**, flagged below.

## What worked
- Confirmed iOS 26 is real and already one generation behind current (iOS 27) as of SDK 58 — no fabricated version numbers.
- Confirmed `expo-glass-effect`'s automatic View-fallback and the two distinct availability-check functions.
- Confirmed `expo-symbols`'s fallback-prop requirement and its Android/web Material-Symbols substitution behavior.

## What did not work / blocked
- Could not confirm `expo-symbols`'s exact minimum iOS version from the fetched page content (likely iOS 13+ for SF Symbols generally, but **do not guess** — re-fetch `docs.expo.dev/versions/v58.0.0/sdk/symbols/` directly, or read the installed package's `expo-module.config.json`/podspec at Phase 1 before relying on a specific floor).
- Could not device-test Reduce Transparency behavior — **blocked: no physical iOS device** (per PREFLIGHT.md §A — only simulator/EAS cloud builds available, and Reduce Transparency + Liquid Glass interaction is best verified on a real device with real GPU/compositor behavior). Mark this specific sub-check `blocked: device`.

## Fallback (already built into the packages; no new decision needed)
- `expo-glass-effect`: automatic `View` fallback pre-iOS-26 / when API unavailable — rely on `isGlassEffectAPIAvailable()`, never assume from OS version string.
- `expo-symbols`: always supply an explicit `fallback` node or platform-keyed name object; never assume SF Symbol names resolve cross-platform.
