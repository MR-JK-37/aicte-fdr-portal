# S-05 — RLS + connection-pool context isolation test design

**Status: Design complete (no implementation — Phase 1's job per MASTER_PROMPT §4.2 spike scope).**

## What this spike is
Not external research. This spike produces the **test design** MASTER_PROMPT §8.5 requires so Phase 1 can implement it directly without re-deriving the approach. §8.5 text (verbatim from MASTER_PROMPT):

> "Per request: open a transaction, `SET LOCAL app.user_id`, `app.role_scope` (JSON of institution_ids / region_ids / assignment ids), `app.assurance` via parameter-safe `set_config(..., true)`. Policies reference these. Provide a **pool-isolation test** that runs interleaved requests of two tenants on a size-1 pool and proves no leakage, plus a test that a missing context yields zero rows. Workers use a distinct DB role with narrowly scoped policies."

## Why this matters
`SET LOCAL` is transaction-scoped in Postgres, not connection-scoped and not session-scoped beyond the transaction. If the application pool ever reuses a physical connection for a second request **without** the first request's transaction having committed/rolled back and cleared its `SET LOCAL` context, or if the pooling layer does session-level pooling (e.g., some PgBouncer modes) where `SET LOCAL`/`SET` state can leak across logical transactions, tenant A's `app.role_scope` could silently apply to tenant B's query — a catastrophic cross-tenant data leak that normal functional tests would never catch because each test runs in isolation, not interleaved.

## Test design

### Test 1 — Interleaved two-tenant leakage test (the core proof)
**Setup:**
- Spin up the real Postgres container (not a mock — MASTER_PROMPT §9/testing section already mandates "Integration against real Postgres ... no mocked repositories for authz or RLS").
- Configure the application's DB connection pool with **max size = 1** (forces every request to share the single physical connection, which is the worst case for context bleed — if isolation holds at pool size 1, it holds at any size).
- Seed two tenants (institution A, institution B) each with at least one row in a table governed by RLS policies keyed on `app.role_scope`'s institution_ids (e.g., the `instruments` table from F-03).

**Execution:**
1. Open two concurrent async tasks/threads, Task A (acting as tenant A's request) and Task B (acting as tenant B's request).
2. Interleave at the statement level, not just the request level — e.g.:
   - Task A: BEGIN; `SET LOCAL app.user_id = 'userA'`, `SET LOCAL app.role_scope = '{"institution_ids":["inst-A"]}'`.
   - **Yield control to Task B before Task A's SELECT runs.**
   - Task B: BEGIN; `SET LOCAL app.user_id = 'userB'`, `SET LOCAL app.role_scope = '{"institution_ids":["inst-B"]}'`.
   - Task B: SELECT * FROM instruments; → assert only inst-B rows returned.
   - Task B: COMMIT (or ROLLBACK).
   - **Yield back to Task A.**
   - Task A: SELECT * FROM instruments; → assert only inst-A rows returned (never inst-B rows, even though Task B's query executed on what may be the same physical connection in between, if the pool reused it).
   - Task A: COMMIT.
3. Repeat the interleave pattern with the order reversed (B starts first, interleaves with A) and with partial overlap (A sets context and queries, B starts mid-A-transaction if the driver/pool allows it — this specifically tests whether `SET LOCAL`'s transaction scoping is actually honored by the pool implementation chosen, e.g. asyncpg pool, SQLAlchemy pool, PgBouncer transaction-mode).
4. Run the whole interleave pattern in a tight loop (e.g., 200–500 iterations) to surface non-deterministic race conditions that a single run would miss — this is consistent with MASTER_PROMPT's general mandate for race-condition-aware testing (§ "Race / money flows" hunting pattern in the security skill set, and the "pool-isolation test" wording itself implies repeated adversarial interleaving, not a single happy-path pass).

**Pass criterion:** In every iteration, every query returns rows scoped **only** to the `app.role_scope` set in that same transaction. Zero cross-tenant rows, zero flaky failures across the full loop count.
**Fail criterion:** Any single iteration where tenant A's query returns a tenant-B row (or vice versa) — this is a release blocker, not a flaky-test-retry situation.

### Test 2 — Missing context yields zero rows (fail-closed proof)
- Open a transaction, deliberately **do not** call `SET LOCAL app.role_scope` (simulate a code path that forgot to set context, or a worker connection that isn't using the request-scoped middleware).
- Run the same SELECT against the RLS-governed table.
- **Pass criterion:** zero rows returned (RLS policy must default-deny when the session variable is unset/null — never fall back to "no filter" / all-rows). This directly implements MASTER_PROMPT's "default deny" non-negotiable (CLAUDE.md rule 6) at the database layer, independent of the application-layer `authorise()` function in §8.4 — defense in depth.
- Also test: context set to an **empty** `institution_ids` array (`'{"institution_ids":[]}'`) — must also yield zero rows, not "all rows" (guards against an empty-array-means-unfiltered policy bug, a common RLS authoring mistake with `= ANY(...)`/`@>` operators).

### Test 3 — Worker role isolation
- Confirm the worker DB role (used for background jobs / outbox dispatch per §8.5's "Workers use a distinct DB role with narrowly scoped policies") **cannot** read/write rows outside its narrowly-scoped policy even when given no `app.role_scope` at all — i.e., the worker role's policies should be scoped by role grants (e.g., only the outbox/notifications tables, or explicit service-level scope), not by trusting a missing app-level variable to mean "everything."

### Test 4 — Same-connection, sequential tenants (non-interleaved control)
- A simpler baseline: on a size-1 pool, run tenant A's full request-response cycle to completion (commit), then tenant B's. Confirm no residual state. This is a cheap sanity check to run first before the expensive interleaved randomized Test 1, since if this control fails, Test 1's failures are not informative about *interleaving* specifically.

## Implementation notes for Phase 1
- Use the actual connection-pool library the backend will use (not yet pinned — record the choice and version in `docs/STACK_LOCK.md` when selected) and verify its pool `acquire`/`release` semantics don't call anything equivalent to `DISCARD ALL`/`RESET ALL` *before* the next logical transaction begins in a way that would mask a real bug — the test must prove isolation under the *actual* pool behavior shipped, not an idealized one.
- If using PgBouncer or another external pooler in production, this test should also run against that pooler's actual mode (session vs transaction vs statement pooling) in at least a staging-like CI job, since `SET LOCAL` behavior differs meaningfully between PgBouncer's transaction-mode (safe, each transaction gets inherited settings cleared at transaction end) and session-mode (unsafe for this use without extra care) — MASTER_PROMPT doesn't name the pooler yet; this is an explicit decision to record before Phase 1 ships RLS code.
- Place this test under integration tests that run against the real Postgres container in CI (per MASTER_PROMPT's testing section), tagged so it always runs on every PR touching `app.role_scope`/RLS policy files.
