# S-04 — Push round-trip: FCM HTTP v1 (Android) + APNs token-auth (iOS)

**Status: Android = PASS (doc-verified, no device send attempted); iOS = `blocked: account` + `blocked: device`.**

## What was tested
Per the spike definition and PREFLIGHT.md §B, this spike cannot be a real device round-trip for iOS (no Apple Developer Program membership, no physical iPhone — confirmed missing items in PREFLIGHT.md §B). For Android, this spike doc-verifies the current official FCM HTTP v1 contract against what MASTER_PROMPT §10.5 already specifies, looking for drift. No actual device send was attempted for either platform in this research pass (that requires live credentials and hardware which Phase 0 does not have and should not fabricate).

## iOS — explicitly blocked
- **`blocked: account`** — no paid Apple Developer Program membership exists in this environment (PREFLIGHT.md §B: "paid Apple Developer Program membership → App ID with Push Notifications capability → APNs Auth Key (.p8) ... Without this, iOS push is `blocked: account`").
- **`blocked: device`** — no physical iPhone available; PREFLIGHT.md states simulator support for push is limited, so even with credentials a round-trip could not be proven on simulator alone.
- MASTER_PROMPT §10.6 already documents the intended contract (HTTP/2 to APNs with `.p8` key, `apns-push-type: alert`, `apns-priority` 10/5, `apns-topic`, `apns-collapse-id`, `thread-id`, `interruption-level` gated on entitlement approval, `category`, token via `expo-notifications` `getDevicePushTokenAsync`, production/sandbox endpoint split, error handling for `BadDeviceToken`/`Unregistered`/`TooManyRequests`/`ExpiredProviderToken` with JWT refresh before 60 minutes). This spike does not add new information here beyond confirming the block is real and documented in both PREFLIGHT.md and MASTER_PROMPT — no device-side verification is possible until an Apple Developer account and a physical iPhone are provided. Phase 1 should build the full server-side APNs integration code against this documented contract and defer only the *live send test* to whenever hardware/credentials arrive, per MASTER_PROMPT §0.4 ("never fake it" — the real workflow should exist and surface "not configured" honestly).

## Android — doc-verified against MASTER_PROMPT §10.5
Checked Firebase's official Cloud Messaging documentation (`firebase.google.com/docs/cloud-messaging/send-message` and related v1 API pages) for drift against §10.5's claims:
- **Authentication**: confirmed FCM HTTP v1 uses a Google **service-account credential exchanged for a short-lived OAuth2 access token** — matches §10.5 exactly.
- **Message shape**: confirmed the v1 API supports a combined `notification` + `data` payload per message, with platform-specific overrides nested under `android.notification.*` and `android.priority` — consistent with §10.5's description of `android.notification.channel_id`, `android.priority`, `ttl`, and `collapse_key`. The literal JSON field names (`notification.channel_id`, `android.priority` = `"high"`/`"normal"`, `android.ttl`, `android.collapse_key`) are the long-standing, stable FCM v1 schema and were not seen to have changed; however, the automated fetch tool returned a summary rather than the literal current reference-page JSON schema for this pass, so **this spike recommends a direct re-read of `https://firebase.google.com/docs/reference/fcm/rest/v1/projects.messages` against the exact backend library version chosen (not yet pinned) before Phase 5 implementation**, to catch any schema change missed by the summarized fetch.
- **Error codes**: §10.5 names `UNREGISTERED`, `INVALID_ARGUMENT`, `QUOTA_EXCEEDED`, `UNAVAILABLE`, `SENDER_ID_MISMATCH`, `THIRD_PARTY_AUTH_ERROR`. These are the documented FCM v1 error-code enum values from Google's own error-codes reference; the exact reference page content could not be fully re-pulled in this pass (tool returned a navigation summary rather than the full enum table) — **flag as a re-check item**, not a drift finding. No contradiction was found; nothing suggests these codes have been renamed or removed.
- **Android app behavior** (`POST_NOTIFICATIONS` runtime permission on Android 13+, channel creation before requesting permission, token refresh/registration lifecycle): consistent with current Android/Firebase guidance; not contradicted by anything found.

## What worked
- Confirmed the FCM v1 auth model and general payload shape match §10.5 with no detected drift.

## What did not work
- Could not pull the literal, current JSON schema reference page or the literal error-code enum table in full via the available fetch tooling (got summaries, not raw reference tables). This is a tooling limitation in this pass, not a finding of drift — **re-verify literal field names and the full error-code table directly from `firebase.google.com/docs/reference/fcm/rest/v1/projects.messages` before writing the FCM adapter in Phase 5**, per CLAUDE.md "verify, don't recall."
- No actual device send was performed (by design — doc-verification only, per the spike's scope; an actual Android emulator/device send is Phase 5+ implementation work, not a Phase 0 doc spike).

## Fallback
None needed — §10.5 as written is consistent with current official docs as far as could be verified; the only action item is the Phase-5 literal-schema re-check noted above, which MASTER_PROMPT §0.3 already requires ("verify, don't recall" for every external API).
