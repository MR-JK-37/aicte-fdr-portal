## 1. What was built (Modules & Deliverables)

### 1.1 Local OCR Assist & Provenance (`F-05`, SPEC §14.1, SPEC §18.1 Scenario 3)
- **Local OCR Engine (`app/documents/ocr.py`)**:
  - Word-level bounding boxes, per-token confidence scores, and page tracking extracted using Tesseract v5 via pytesseract.
  - Graceful fallback: when OCR is disabled (`DISABLE_OCR=1`) or unavailable, the system reports `UNAVAILABLE` honestly rather than simulating false success.
- **Provenance Candidate Extraction (`app/documents/extraction.py`)**:
  - `RegexFDRExtractor` with `extract_with_provenance()` extracting candidate fields (`instrument_number`, `amount`, `dates`, `bank_name`, `ifsc`) with page number, bounding box coordinates (`x0, y0, x1, y1`), and confidence scores.
- **Review & Correction Workflow (`app/documents/router.py`)**:
  - `POST /v1/documents/{id}/extract`: Runs OCR and extracts candidate fields.
  - `GET /v1/documents/{id}/extraction`: Returns candidate extraction with honest state (`UNAVAILABLE`, `PENDING_SOURCE`, `CANDIDATE`, `CONFIRMED`).
  - `POST /v1/documents/{id}/extraction/review`: Side-by-side human review allowing officer/submitter to correct misread fields.
- **Evidence Ladder Invariant**:
  - OCR extraction proposes candidate fields only.
  - Human confirmation (`confirm_extraction`) advances the instrument to `L1_EXTRACTED`.
  - Under no circumstances does OCR extraction or human correction advance an instrument to `L2_BANK_CONFIRMED` or `L3_LEDGER_RECONCILED`.

### 1.2 Bank Confirmation Requests & Evidence Decision (`F-06`, SPEC §8.3, SPEC §18.1 Scenario 4)
- **Bank Confirmation Lifecycle (`app/verification/router.py`)**:
  - Bureau officers issue confirmation requests (`POST /v1/verification/bank-requests`) generating unique tracking numbers.
  - Tenant and bank isolation: Bank verifiers can only list and inspect requests for their assigned participating bank (`AppRole.BANK_VERIFIER`).
  - Participating bank responds (`POST /v1/verification/bank-requests/{id}/respond`) with verified amounts, CBS account numbers, and confirmation notes.
- **Independent Evidence Decision & SoD (`POST /v1/verification/bank-requests/{id}/decision`)**:
  - Independent bureau officer evaluates evidence.
  - `ACCEPT`: Advances instrument to `L2_BANK_CONFIRMED`, creates `VerificationRecord`, and appends audit entry.
  - `INCONCLUSIVE`: Never labels institution as fraudulent. Sets status to `INCONCLUSIVE` and automatically opens a `ReconciliationException` with status `OPEN`.
  - Separation of Duties (SoD): The officer who requested bank confirmation cannot act as the decision maker (`SeparationOfDutiesError`, 403 Forbidden).
- **Escalation Notification (`POST /v1/verification/bank-requests/{id}/escalate`)**:
  - Issues escalation notification for overdue requests without changing instrument status to rejected.

### 1.3 Bank Statement Import & Deterministic Reconciliation Engine (`F-07`, SPEC §8.3, SPEC §18.1 Scenario 5)
- **Multi-Format Statement Parser (`app/statements/parser.py`)**:
  - Supports SWIFT MT940 (Tag 61 statement lines), ISO 20022 CAMT.053 XML (`<Ntry>` records), and standard CSV formats.
  - Malformed row quarantine: Unparseable amounts or corrupted dates are quarantined with exact line numbers and error reasons into batch metadata without aborting valid lines.
- **Deterministic Reconciliation Engine (`app/statements/router.py`)**:
  - SHA-256 batch checksum idempotency check: Re-importing identical files returns existing batch data without duplicating rows.
  - Exact match (`exact_utr_amount`): Exact UTR + amount match against `ONLINE_SD` instruments promotes instrument to `L3_LEDGER_RECONCILED` and creates `VerificationRecord`.
  - Invariant: FDR scans can NEVER produce `L3_LEDGER_RECONCILED`.
  - Ambiguous matches (divergent amounts or multiple instrument candidates) route to `ReconciliationException` with status `AMBIGUOUS` and NEVER auto-confirm.
  - Exception resolution endpoint (`POST /v1/statements/exceptions/{id}/resolve`).

### 1.4 Discrepancy & Completeness Rule Engine (`F-08`, SPEC §14.1, PS Scenario "Discrepancy Identification")
- **Rule Evaluator (`app/rules/discrepancies.py`)**:
  - Versioned rules (`RULE_VERSION = "discrepancy-v1.0"`) evaluating:
    - `RULE_AMOUNT_MISMATCH`: Declared amount vs document extracted amount.
    - `RULE_DATE_INCONSISTENCY`: Issue date >= Maturity date.
    - `RULE_EXPIRED_INSTRUMENT`: Maturity date in the past.
    - `RULE_INVALID_IFSC`: Non-standard 11-character RBI IFSC pattern.
    - `RULE_DUPLICATE_INSTRUMENT_NUMBER`: Cross-institution duplicate instrument numbers.
- **Discrepancy Router (`app/discrepancies/router.py`)**:
  - `GET /v1/instruments/{id}/discrepancies`: Returns active discrepancies with severity (`CRITICAL`, `WARNING`, `BLOCKING`).
  - `POST /v1/instruments/{id}/discrepancies/evaluate`: Evaluates rules and upserts open `Discrepancy` records.
  - Invariant: Rule engine NEVER automatically rejects an instrument or labels an institution as fraudulent.
  - Officer conversion (`POST /v1/instruments/{id}/discrepancies/{id}/generate-observation`): Converts identified discrepancy into a formal `ScrutinyObservation` (`F-09`) with status `OPEN`.
  - Officer acknowledgment (`POST /v1/instruments/{id}/discrepancies/{id}/acknowledge`): Acknowledges discrepancy with documented rationale.

### 1.5 Structural Invariants & AST Proofs (`tests/test_verification_invariants.py`)
- Verified mathematical and logical ladder constraints:
  - FDR instruments never reach `L3_LEDGER_RECONCILED` from statement reconciliation.
  - Separation of duties strictly enforced against self-approval.
  - Static AST inspection across all Python source files guaranteeing that `L2_BANK_CONFIRMED` and `L3_LEDGER_RECONCILED` assignments only occur within authorized verification and reconciliation modules.
