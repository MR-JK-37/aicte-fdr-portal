## 1. What was built (Modules & Deliverables)

### 1.1 In-App Inbox First & Multi-Stage State Tracking (`F-14`, SPEC §10, §11)
- **Database Schema & Models (`migrations/...d7e8f9a0b1c2_phase5_notifications_and_realtime.py`, `app/models/workflow.py`)**:
  - `user_notifications`: In-app persistent inbox decoupled from external push delivery. Includes tenant/institution scoping, recipient user reference, event correlation (`domain_event_id`, `instrument_id`, `observation_id`, `release_request_id`), localized category, action deep link, and explicit timestamps (`read_at`, `acknowledged_at`, `actioned_at`).
  - `notification_attempts`: Individual delivery attempts per channel/device tracking honest stage progression:
    `CREATED` -> `QUEUED` -> `PROVIDER_ACCEPTED` | `PROVIDER_FAILED` -> `DEVICE_RECEIVED` -> `OPENED` -> `ACKNOWLEDGED` -> `ACTIONED`.
  - `device_installations`: Device token lifecycle tracking (`token`, `platform` [ANDROID/IOS/WEB], `provider` [FCM/APNS/WEBPUSH], `is_active`, `revoked_at`, `revocation_reason`).
  - `notification_preferences`: User channel enablement, quiet hours window (`quiet_hours_start`, `quiet_hours_end`, `quiet_hours_timezone`), and category opt-outs.
  - `sse_events`: Replay buffer for Server-Sent Events with monotonically increasing `id` sequence for `Last-Event-ID` catch-up.
  - `notification_dlq`: Dead-Letter Queue recording terminal delivery failures with error details, retry count, and replay capability.

### 1.2 Channel Adapters & Honest Reporting (`F-14`, SPEC §10.3, §10.5)
- **Push & Transport Adapters (`app/notifications/adapters/`)**:
  - `base.py`: Strongly-typed `PushPayload` and `SendResult` data models.
  - `fcm.py`: Firebase Cloud Messaging HTTP v1 adapter for Android with OAuth2 token caching, proper priority headers, and automated device token revocation on `UNREGISTERED` or `INVALID_ARGUMENT`.
  - `apns.py`: Apple Push Notification service (APNs) HTTP/2 token-auth adapter for iOS with ES256 JWT generation, topic headers, and revocation on `410 Unregistered` or `400 BadDeviceToken`.
  - `webpush.py`: Web Push adapter with VAPID authorization headers (`crypto_key`, RFC 8292 claims), and revocation on `410 Gone` or `404 Not Found`.
  - `email.py`: Transactional email delivery adapter.
- **Honest Provider Semantics**:
  - Unconfigured credentials honestly report `status="NOT_CONFIGURED"`, avoiding fabricated "delivered" badges and preventing system crashes.
  - `PROVIDER_ACCEPTED` is recorded strictly upon valid external gateway 200/202 responses with provider message IDs, explicitly decoupled from client receipt or user opening.

### 1.3 Lock-Screen Privacy & Canary String Protection (SPEC §10.4, SPEC §18.1 Scenario 10)
- **Versioned & Localized Templates (`app/notifications/templates.py`)**:
  - Full multi-lingual templates supporting English (`en`), Hindi (`hi`), and Tamil (`ta`).
  - Strict privacy separation:
    - **Lock-screen Banner**: Generic static strings (e.g., "AICTE FDR Portal — Action Needed", "नई कार्रवाई आवश्यक है") with zero PII, zero FDR numbers, zero amounts, and zero bank names.
    - **Authenticated In-App Inbox**: Contextual details formatted safely using `SafeDict` to prevent formatting errors and canary leakage.
  - Validated with automated test suites asserting zero leakage of canary strings (e.g. `CANARY-FDR-987654321`, `₹50,00,000`, `State Bank of India`) in lock-screen push payloads.

### 1.4 Dynamic Recipient Resolution & Statutory Non-Suppression (`F-14`, SPEC §10.6, §11)
- **Scope-Driven Recipient Resolution (`app/notifications/resolver.py`)**:
  - Recipients resolved dynamically from the current DB state for each institution/event scope. Never relies on stale cached lists.
- **Statutory Override Invariant**:
  - Categories classified as statutory compliance (`critical_workflow`, `deadline`, `security_account`) **strictly bypass** quiet hours and category opt-outs.
  - Regulatory notices cannot be suppressed by user configuration.

### 1.5 Real-Time Server-Sent Events (`F-15`, SPEC §10.2)
- **Stream Endpoint (`GET /v1/stream`)**:
  - Standard Server-Sent Events protocol with 15-second keepalive heartbeats (`: keep-alive`).
  - `Last-Event-ID` Catch-Up: Replays missed events from `sse_events` on client reconnect.
  - Per-Event Re-authorization: Each replayed or streamed event dynamically re-verifies tenant/user authorization prior to emission.

### 1.6 Device Lifecycle & Logout Invalidation (SPEC §10.5, SPEC §18.1 Scenario 10)
- **Device Management (`app/notifications/devices.py`)**:
  - Registration (`POST /v1/devices/register`) and revocation (`POST /v1/devices/{token}/revoke`).
  - Automatic logout revocation: `POST /v1/auth/logout` revokes all active device tokens associated with the user, ensuring subsequent push dispatches to those devices receive nothing.

### 1.7 Resiliency, DLQ & Funnel Metrics (`F-14`, SPEC §18.1 Scenario 14)
- **Outage & Error Recovery (`app/notifications/pipeline.py`)**:
  - Network timeouts and 5xx provider failures are recorded as `PROVIDER_FAILED` with `TRANSIENT` category and routed to retry / `notification_dlq`.
  - Invalid tokens are recorded as `PERMANENT` errors and immediately trigger device token revocation.
- **Funnel & DLQ Endpoints (`app/notifications/router.py`)**:
  - `GET /v1/notifications/funnel`: Metrics breakdown by stage (`created`, `queued`, `provider_accepted`, `provider_failed`, `opened`, `acknowledged`, `actioned`).
  - `GET /v1/notifications/dlq`: Admin inspection of dead-lettered notices.
  - `POST /v1/notifications/dlq/{id}/replay`: Replays failed notifications.
