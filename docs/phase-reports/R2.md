# Stream R2 — Authentication and the 13 roles (2026-10-24)

## Scope actually covered across this stream's three slices
**Slice 1:** closed a complete authentication bypass found by inspection (not assumed — read the
actual code first), and built the real password + TOTP machinery it needed to exist for real.
**Slice 2:** real session management — `app_sessions` table, refresh-token rotation with reuse
detection, `GET/DELETE /auth/sessions`, `POST /auth/logout-all`. **Slice 3:** `GET /me/navigation`
(server-built per-role sidebar/tab manifest) and `GET /me/profile-completion` +
`PATCH /me/profile` (real completion percentage from real DB fields, no fabricated progress).
The much larger remaining scope (passkeys, invitations, recertification, the 12-role staging seed
+ E2E walkthrough, web/mobile sign-in UI, the generated negative permission matrix,
role-differentiated idle/absolute timeouts) is **not** done — see "Carried forward".

## What was found (read before assumed broken, per CLAUDE.md "verify, don't recall")
- **`POST /v1/auth/login` had no password check whatsoever.** `app/auth/router.py`'s `login()`
  looked up the user by e-mail and minted a real, valid access token — `req.password` was received
  by the schema but never read. `tests/test_auth_router.py::test_login_success` literally passed
  the password `"any_password_for_dev"` and asserted success, actively protecting the bypass as if
  it were a feature (the same pattern found in R0/R1's web/mobile mocks).
- **`POST /v1/auth/step-up` accepted any syntactically-valid 6-digit code.** The comment read "In
  dev/test, any 6-digit OTP code grants 15 minutes step-up validity" with no actual `env` check
  distinguishing dev/test from production — it was unconditional in all environments.
- **No credential storage existed at all.** `AppUser` (`app/models/core.py`) had `keycloak_sub`,
  `mfa_enrolled` (a bare boolean with nothing backing it), and `step_up_valid_until`, but no
  `password_hash`, no TOTP secret column, no lockout tracking, no recovery codes. `keycloak_sub` is
  vestigial — nothing in the codebase ever verifies a Keycloak-issued token; `get_current_principal`
  (`app/auth/deps.py`) only ever decodes this API's own self-issued HS256 JWT.
- **ADR-001 resolved**: given (a) the 13-role model, `ROLE_PERMISSIONS_MATRIX`, and RLS are already
  correctly built around `AppUser` as the source of truth, (b) zero real Keycloak integration code
  exists despite the realm JSON and docker-compose service being present, and (c) the realm JSON
  (`infra/keycloak/fdr-realm.json`) and `scripts/setup_keycloak.py` still encode the **old 8-role
  model**, stale relative to the real 13-role `AppRole` enum — completing the existing self-hosted
  module is the lower-risk, more-realistic path. Keycloak stays available for a future SSO/D-08
  federation decision but is not the active identity provider. This supersedes ADR-001's
  "provisional" framing from R0 — it's now a final call, not a placeholder.

## What was built
- **Migration `c3d4e5f6a7b8`**: adds `password_hash`, `totp_secret_encrypted`,
  `failed_login_count`, `locked_until`, `recovery_codes_hashed` to `app_users`. Verified
  up → down → up on the real dev DB (`alembic upgrade head` / `downgrade -1` / `upgrade head`),
  full test suite re-run clean after the round-trip.
- **`app/auth/security.py`** (new): `hash_password`/`verify_password` (argon2id via
  `argon2-cffi`), `encrypt_totp_secret`/`decrypt_totp_secret` (Fernet, keyed from
  `settings.totp_encryption_key` — a fixed, public dev default; **not yet rejected by prod_guard
  for a real deployment, flagged below**), `generate_totp_secret`/`verify_totp_code`/
  `totp_provisioning_uri` (`pyotp`), `generate_recovery_codes`/`hash_recovery_code`,
  `is_locked`/`lockout_expiry`.
- **`POST /v1/auth/login`**: now verifies the password hash; if the account has TOTP enrolled, also
  requires a valid `totp_code` in the same request (a single-call login+MFA, not the spec's
  separate challenge-screen flow — see "Carried forward"). Generic "Invalid credentials" for both
  unknown e-mail and wrong password (no account enumeration, AUTH_ROLES_MATRIX §2.2(1)). Lockout:
  `failed_login_count` increments on failure, locks for `settings.lockout_minutes` after
  `settings.max_login_attempts` (defaults 10/15, matching AUTH_ROLES_MATRIX §2.2(8)).
- **`POST /v1/auth/step-up`**: now requires the account to have TOTP enrolled and a real,
  current TOTP code — no longer accepts arbitrary 6-digit input.
- **`POST /v1/auth/mfa/enrol/start`** / **`POST /v1/auth/mfa/enrol/confirm`** (new): real TOTP
  enrolment. `start` returns a candidate secret + provisioning URI (for a QR code) but persists
  nothing; `confirm` requires a real code against that secret before the (encrypted) secret and 10
  hashed recovery codes are stored — an abandoned enrolment never leaves a usable secret in the DB.
- **`tests/test_auth_router.py`**: fully rewritten — 12 tests, including the specific regression
  tests that prove the bypass is closed (`test_login_rejects_any_password_when_none_set`,
  `test_login_locks_account_after_max_attempts`, `test_step_up_requires_real_totp_not_any_six_digits`,
  `test_login_with_mfa_enrolled_requires_totp`, `test_mfa_enrolment_flow`).
- Regenerated `packages/api-client/openapi.json` and `src/generated/schema.d.ts` (`make openapi`
  + `pnpm generate`), per CLAUDE.md's definition of done.

### Slice 2 — real session management
- **Migration `d4e5f6a7b8c9`**: new `app_sessions` table (`refresh_token_hash`,
  `previous_token_hash`, `device_label`, `ip_area`, `created_at`, `last_seen_at`, `expires_at`,
  `revoked_at`), RLS-enabled (same `is_bureau_role() OR app_user_id = current_app_user_id()`
  pattern as `device_tokens`/`consent_records`). Verified up → down → up.
- **`create_access_token`** now embeds a `session_id` claim; **`Principal`** (`app/authz.py`)
  carries `session_id` so handlers know which session issued the current request.
- **`POST /v1/auth/login`** now creates a real `AppSession` row and returns both an access token
  (15 min, `settings.access_token_expiration_seconds`, renamed from the old unused-everywhere-else
  `jwt_expiration_seconds`) and a refresh token (30 days, `settings.refresh_token_expiration_days`
  — AUTH_ROLES_MATRIX §2.2(9)). Web gets both as separate `httponly` cookies
  (`fdr_session`, `fdr_refresh`); the refresh token is also returned in the JSON body for mobile.
- **`POST /v1/auth/refresh`** (new): real rotation — presenting the current refresh token issues a
  new access+refresh pair and advances the session's `refresh_token_hash` (keeping the old one as
  `previous_token_hash`). Presenting an **already-rotated-out** token (`previous_token_hash` match,
  not current) is treated as theft/reuse and immediately revokes that session — not just rejects
  the one request.
- **`GET /v1/auth/sessions`** (new): lists the caller's own active, non-expired sessions, with a
  `current: true` flag on the session the request's own access token belongs to.
- **`DELETE /v1/auth/sessions/{id}`** (new): revokes one session. Cross-user id → 404 (not 403 —
  tested explicitly, `test_session_revoke_cross_user_returns_404`).
- **`POST /v1/auth/logout-all`** (new): revokes every session for the caller in one call
  ("sign out everywhere", AUTH_ROLES_MATRIX §2.2(7)).
- **`logout`** now also revokes the caller's own session row (previously only cleared the cookie
  and revoked push-notification device tokens).
- **Bug found and fixed in the same slice**: the first version of this code 500'd on every login,
  because `set_app_context`'s Postgres GUCs are `SET LOCAL` (transaction-scoped) and `login()` did
  an intermediate `db.commit()` (to persist the lockout-counter reset) before the RLS-protected
  `app_sessions` insert — the commit silently ended the transaction the role context was set for,
  so the insert ran with no `app.role` set and RLS correctly rejected it. Fixed by re-establishing
  `set_app_context` immediately before the session insert. Caught by running the new tests, not
  assumed fixed — all 6 new session tests plus the original 12 pass together.
- `tests/test_auth_router.py` grew from 12 to **18 tests**: refresh rotation, reuse detection
  (including that reuse revokes the *whole* session, not just the presented token), garbage-token
  rejection, session list/current-flag, cross-user revoke 404, logout-all.

### Slice 3 — navigation manifest and profile completion
- **`app/auth/navigation.py`** (new): `AUTH_ROLES_MATRIX.md` §1 turned into data — one
  `RoleNavigation` (landing route, web sidebar, mobile tabs) per role, each `NavItem` carrying a
  logical `key`/`icon_key`/`route`/`required_permission` (no hard-coded role branching in any
  client — AUTH_ROLES_MATRIX §2.3). Covers all 12 human roles from the matrix table;
  `INTEGRATION_SERVICE` (machine identity, no UI) intentionally has no entry.
- **`GET /v1/me/navigation`** (new): returns the caller's own manifest. Routes/icons are logical
  identifiers for screens R5/R6 haven't built yet — the manifest describes what the role is
  *entitled* to see, which is correct to publish even before the screen exists.
- **Migration `e5f6a7b8c9d0`**: adds `designation`, `mobile_number`, `mobile_verified` to
  `app_users` — profile-completion had no real fields to read before this.
- **`GET /v1/me/profile-completion`** (new): percent + per-item completion computed from real DB
  columns (`full_name`, `designation`, `mobile_verified`, `preferred_language`, `mfa_enrolled`),
  not fabricated. `mobile_verified` is always `False` — no SMS/OTP provider is configured
  (`docs/PREFLIGHT.md`) and nothing in this codebase ever sets it `True`; this is intentional
  honesty (the checklist item should show incomplete until that's real), not a bug to "fix" by
  faking verification. `passkey` is listed as an explicit `optional: true` item, always incomplete
  (no passkey system exists), and never counted in the percentage denominator.
- **`PATCH /v1/me/profile`** (new): self-service update of `full_name`/`designation`/
  `mobile_number`/`preferred_language`. Setting a new `mobile_number` resets `mobile_verified` to
  `False` (correct invariant once real verification exists, even though nothing sets it `True`
  yet). Audited (before/after) via the existing `append_audit_entry`.
- `tests/test_auth_router.py` grew from 18 to **22 tests**: role-specific navigation (two
  different roles get genuinely different manifests, asserted by inequality), unauthenticated
  navigation request rejected, profile-completion reflects real fields including the two items
  that must stay incomplete, `PATCH /me/profile` persists and is self-scoped.

## Found but NOT fixed this session (flagged, not silently left)
- **`app/auth/deps.py` lines ~111–119**: `BANK_VERIFIER` role scope (`role_scope_dict["bank_name"]`)
  is derived by checking whether the authenticated user's **own e-mail address contains the
  substring** `"@sbi."`, `"@pnb."`, `"@hdfc."`, or `"@icici."` — not validated against any real,
  onboarding-approved bank-domain allowlist. An account with e-mail `attacker@sbi.evil.com` would
  be granted State Bank of India's verifier scope. This predates this session (not introduced by
  it) but is exactly the kind of authorization bug R2's own scope exists to close — tracked for the
  next R2 session, not fixed here because a correct fix needs the bank-onboarding domain-allowlist
  data model, which doesn't exist yet.
- `settings.totp_encryption_key` has a fixed, checked-into-the-repo dev default — fine for
  local/test, a real security hole if it ever reached production unchanged.  `app/core/prod_guard.py`
  should refuse this default the same way it refuses the known simulation flags; not done this
  session.

## Carried forward — explicitly NOT done yet
Per `docs/AUTH_ROLES_MATRIX.md` §2–§4 and `docs/MASTER_PROMPT_V2.md` R2.1–R2.7, still open:
1. **Passkeys / WebAuthn** (register + login).
2. **Separate login → MFA-challenge screens** — login is single-call (password + optional TOTP in
   one request) rather than a password step then a distinct challenge screen. Functionally closes
   the bypass; UX-wise diverges from the spec's two-screen flow (R2.4/R2.5's job to build the real
   screens around whichever shape the UI needs — may be worth revisiting the API shape then).
2b. **Recovery-code login** (the codes are generated and hashed; nothing yet accepts one as an
    alternate factor).
3. **Role-differentiated idle/absolute session timeouts** — AUTH_ROLES_MATRIX §2.2(9) wants staff
   15min/8h, institution 30min/12h, bank verifier 15min/8h; this session implemented one uniform
   30-day absolute expiry for all roles (sessions table + rotation/reuse-detection are real and
   role-agnostic; the *duration policy* isn't role-differentiated yet). Idle timeout (vs. just
   absolute `expires_at`) isn't enforced at all yet either.
4. **Password reset/change, forgot-password**, invitation acceptance — no endpoints exist.
5. **`manage_roles`/role-assignment maker-checker**, recertification campaigns, `IAM_ADMIN`
   endpoints.
6. **Web (`/login`, MFA enrolment wizard, step-up sheet, session list) and mobile sign-in screens**
   — zero auth UI exists on either client; both still have no way to actually call any of this,
   even though `GET /me/navigation`/`GET /me/profile-completion` now exist for them to render from.
7. **`make seed-staging`** and the per-role e2e walkthrough (`e2e:roles`) across all 12 human
   roles — none of this exists yet.
8. **Generated negative role×verb×scope test matrix** driven from the `role_permissions` DB table
   (R2.7) — `test_authz_negative_matrix.py` already exists and passes but wasn't audited this
   session for whether it's hand-written or truly generated/exhaustive.
9. **`infra/keycloak/fdr-realm.json` / `scripts/setup_keycloak.py`** still encode the stale
   8-role model — should be deleted or updated to reflect that Keycloak isn't the active identity
   provider (ADR-001), to stop them misleading a future reader.
10. **`app/auth/navigation.py`'s route/icon keys are not yet cross-checked against anything** —
    they're a reasonable reading of AUTH_ROLES_MATRIX §1, but no screen exists yet to confirm the
    route strings match what R5/R6 actually build; expect to adjust them then, not treat them as
    final URLs now.
