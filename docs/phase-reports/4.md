## 1. What was built (Modules & Deliverables)

### 1.1 Policy Registry (`F-13`, SPEC §2.1–§2.3, §21)
- **Draft-Only Policy Imports (`app/policy/loader.py`)**:
  - Importer loads JSON policy configurations from `config/policy-drafts/` as `draft` or `BLOCKED` status:
    - `aph-2024-27.table-1.4.draft.json`: Table 1.4 security deposit norms across institute types.
    - `aph-2024-27.release-6.46.draft.json`: Clause 6.46 release criteria checklist and clearance requirements.
    - `reminders.example.json`: T-90, T-60, T-30, T-7, T-0 reminder notification schedule.
    - `penalties.blocked.json`: Marked with status `BLOCKED: awaiting AICTE written confirmation (D-01)`.
- **Policy Approval & Maker-Checker Governance (`app/policy/service.py`)**:
  - Unapproved or draft policies cannot drive production regulatory decisions.
  - Policy approval requires different user than author (strict Maker-Checker SoD).
  - Approver must possess `COMPETENT_AUTHORITY` or `PLATFORM_OPERATOR` role.
  - Step-up MFA session or valid 6-digit TOTP token required to approve policy versions.
  - Blocked policies cannot be approved until written authority confirmation is registered.
- **Policy Router (`app/policy/router.py`)**:
  - `GET /v1/policies`: Lists policy versions filtered by `policy_id` or `status`.
  - `GET /v1/policies/{id}`: Detailed inspection of policy version and config payload.
  - `POST /v1/policies/import-drafts`: Imports JSON policy drafts.
  - `POST /v1/policies/{id}/approve`: Approves policy version with Step-up MFA.

### 1.2 Lifecycle, Deadline & Escalation Engine (`F-10`, SPEC §9, SPEC §18.1 Scenario 7)
- **DB-Leased Singleton Scheduler (`app/reminders/scheduler.py`)**:
  - Distributed worker coordination via `scheduler_runs` table with leasing semantics (`acquire_scheduler_lease`).
  - Worker heartbeat tracking (`record_heartbeat`) preventing concurrent duplicate scans.
  - Outage detection (`check_scheduler_health`): Heartbeat gap exceeding threshold generates an explicit `OUTAGE_ALERT` admin event without silently skipping schedules.
- **Obligation Scans & Deterministic Reminders**:
  - Scans instruments for maturity windows: T-90, T-60, T-30, T-7, T-0.
  - Transitions instruments: `ACTIVE` -> `EXPIRING` at T-90; `EXPIRING`/`ACTIVE` -> `MATURED` at T-0.
  - Missing approved schedule in DB generates an explicit admin alert (`NO_APPROVED_SCHEDULE`) and refuses to invent unverified reminder intervals.
  - Idempotency key per SPEC §9: `instrument+event+target_date+schedule_version+recipient`, backed by DB unique constraint `uq_reminder_instrument_window` preventing duplicate reminders across repeated runs.
- **Non-destructive Supervisor Escalation**:
  - Overdue verification and observation casework triggers supervisor notifications without auto-closing or rejecting business entities.

### 1.3 Renewal & Replacement Lineage (`F-11`, SPEC §6.1, SPEC §18.1 Scenario 8)
- **Lineage Service (`app/renewals/service.py`)**:
  - Links predecessor and successor instruments via `instrument_lineage` table (`RENEWAL` or `REPLACEMENT`).
  - Date gap and overlap calculation:
    - Gap days: `max(0, (successor.issue_date - predecessor.maturity_date).days)`.
    - Overlap days: `max(0, (predecessor.maturity_date - successor.issue_date).days)`.
  - Discrepancy & Observation Auto-creation: If gap exceeds policy-allowed grace period (`policy_allowed_gap_days`), automatically creates a `Discrepancy` and opens a casework `ScrutinyObservation`.
  - Lineage state transition: Predecessor transitions to `SUPERSEDED` only when successor reaches `ACTIVE_TRACKING` under approved checks (`on_successor_reaches_active`).
  - DAG Cycle Rejection: Cycle-detection traversal (`assert_no_cycle`) rejects cyclical chains (`A -> B -> A` or self-referential `A -> A`) with `LineageCycleError` at both service and DB levels.
- **Renewals Router (`app/renewals/router.py`)**:
  - `POST /v1/instruments/lineage`: Establishes verified predecessor-successor link.
  - `GET /v1/instruments/{id}/lineage`: Returns lineage graph with predecessors and successors.

### 1.4 Release/Refund Workflow & Execution Evidence (`F-12`, SPEC §2.2, §18.1 Scenario 9)
- **Clause 6.46 Release Checklist (`app/release/service.py`)**:
  - Initialized from approved policy version or default statutory requirements.
  - Individual items updated (`update_checklist_item`) with reason and evidence reference. Bulk-ticking is strictly prohibited.
  - Statuses: `SATISFIED`, `NOT SATISFIED`, `PENDING SOURCE`, `NOT APPLICABLE`.
- **Inter-Cell Clearances (`clearances` table)**:
  - Tracks NOC and clearance from PGRC, Vigilance Cell, Legal Cell, and Regional Office.
  - Verified and recorded individually via `record_clearance_outcome`.
- **Maker-Checker & Delegation Limit Approval**:
  - Scrutiny recommendation (`submit_recommendation`): Recommender cannot be the original release requester (`MakerCheckerViolation`).
  - Competent Authority approval (`decide_release`):
    - Recommender, requester, and scrutiny officer who handled instrument are barred from approving (`MakerCheckerViolation`).
    - Delegation limits enforced: Instrument amount cannot exceed approver's financial threshold (`DelegationLimitExceededError`).
    - Step-up MFA mandatory: Active step-up session or 6-digit TOTP required (`StepUpRequiredError`).
    - Completeness gate: Incomplete checklist items or pending clearances block approval (`ChecklistIncompleteError`).
- **Two-Person Execution Evidence Verification & Discharge**:
  - Approval transitions request to `EXECUTION_PENDING` (instrument remains undispatched/matured).
  - Finance officer records trusted payout proof (`record_execution_evidence`, UTR / RTGS bank reference).
  - Second-person review (`verify_execution_and_discharge`): Independent finance reviewer confirms bank statement execution. Same officer who recorded payment proof cannot review (`ExecutionReviewViolation`).
  - On independent confirmation, release request transitions to `RELEASED_DISCHARGED`, and instrument transitions to `RELEASED` -> `DISCHARGED`.
- **Release Router (`app/release/router.py`)**:
  - Endpoints covering request creation, checklist item update, clearance recording, scrutiny recommendation, CA decision, execution evidence recording, and discharge verification.

### 1.5 State Machines 4 & 5 (`app/lifecycle.py`)
- **Machine 4 (Instrument Transitions)**:
  - Added legal transitions to `SUPERSEDED` from `ACTIVE`, `ACTIVE_TRACKING`, `EXPIRING`, `MATURED`, `RENEWAL_REQUESTED`, `REPLACEMENT_REQUESTED`.
  - Added `InstrumentStatus.RELEASED -> InstrumentStatus.DISCHARGED` transition authorized for `AppRole.FINANCE_VERIFIER`, `AppRole.PLATFORM_OPERATOR`, and `bureau_admin`.
- **Machine 5 (Release Request Transitions)**:
  - Formally implemented `RELEASE_REQUEST_TRANSITIONS`:
    - `DRAFT` -> `SUBMITTED`, `CANCELLED`
    - `SUBMITTED` -> `COMPLETENESS_REVIEW`, `SCRUTINY_RECOMMENDATION`, `RETURNED`
    - `COMPLETENESS_REVIEW` -> `SCRUTINY_RECOMMENDATION`, `RETURNED`, `REJECTED`
    - `SCRUTINY_RECOMMENDATION` -> `CA_APPROVAL`, `EXECUTION_PENDING`, `RETURNED`, `DEFERRED`, `REJECTED`
    - `CA_APPROVAL` -> `EXECUTION_PENDING`, `RETURNED`, `DEFERRED`, `REJECTED`
    - `EXECUTION_PENDING` -> `RELEASED_DISCHARGED`, `DEFERRED`
  - Validated by `assert_release_request_transition_allowed` and `apply_release_request_transition`.
