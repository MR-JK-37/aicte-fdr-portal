## 2026-10-23 (cont'd) — Phase 2

- Full schema (19 tables + enums) via SQLAlchemy models + two Alembic
  migrations: `b35cb080c98c` (initial schema, autogenerated) and
  `a821603301c6` (RLS policies + audit immutability, hand-written SQL).
- **Key finding, caught by test failure, not assumption:** the official
  `postgres` image's `POSTGRES_USER` is a Postgres *superuser*, and
  superusers always bypass RLS regardless of `FORCE ROW LEVEL SECURITY`.
  First RLS test run passed with zero isolation enforced — tests caught it.
  Fix: migration now creates an unprivileged `fdr_app` role
  (`NOSUPERUSER NOBYPASSRLS`) that the API/worker/beat connect as; `fdr`
  (superuser) is used only by Alembic. Compose has a one-shot `migrate`
  service that runs first and gates `api`/`worker`/`beat` via
  `service_completed_successfully`.
- RLS model: Postgres session GUCs `app.role` / `app.institution_id` /
  `app.user_id`, set per-request by `app/db.py:set_app_context` (SET LOCAL,
  transaction-scoped). Policy `tenant_isolation` on every institution-keyed
  table: bureau-side roles (scrutiny_officer, verifier, regional_officer,
  competent_authority, bureau_admin, auditor) see everything; `institution`
  role sees only rows matching its own institution_id; with no context set,
  defaults closed (verified by test — zero rows returned, not all rows).
  `banks`/`branches` are shared reference data, intentionally left without
  RLS; `bank_user` tenant-scoping by branch is deferred to Phase 5
  (verification/bank-portal work), not yet implemented — noted as a gap.
- Audit log: hash-chained (`app/audit.py`), each row's hash commits to the
  previous row's hash + its own content; `audit_log` has a DB trigger
  rejecting UPDATE/DELETE outright (even for the table owner — only a true
  superuser can disable the trigger, which is itself the tamper path the
  test proves detection against).
  **Second bug caught by the test, not assumed fixed:** `verify_chain`
  initially returned a false negative on a tampered row because
  SQLAlchemy's identity map served the pre-tamper cached object instead of
  re-reading it; fixed with `populate_existing=True`. Without the test
  actually asserting on tamper detection (not just "it probably works"),
  this would have shipped broken.
- Keycloak: realm `fdr-portal` provisioned via `scripts/setup_keycloak.py`
  (idempotent, admin REST API, no external login — uses the
  Compose-provided bootstrap admin). Created all 8 roles and one demo user
  per role. Officer roles (scrutiny_officer, verifier, regional_officer,
  competent_authority, bureau_admin, auditor) get `CONFIGURE_TOTP` forced
  as a required action at user-creation time; `institution`/`bank_user` do
  not. Verified live: password-grant login for an officer account fails
  with "Account is not fully set up" until TOTP is configured; confirmed
  via the admin API that only officer accounts carry `CONFIGURE_TOTP` in
  `requiredActions`.
- Tests: `services/api/tests/` — 6 passing (`test_rls.py`,
  `test_audit_chain.py`), run against the live Compose Postgres as the
  `fdr_app` role (not the migration superuser), matching production access.

## 2026-10-23 (cont'd) — Phase 3

- Lifecycle state machine (`app/lifecycle.py`): explicit allow-list graph
  (`TRANSITIONS`) of (from_status -> to_status -> allowed roles); anything
  not in the graph raises `IllegalTransitionError` unconditionally — no
  default-allow path. Every transition requires a non-empty `reason` and
  writes a hash-chained audit entry via `append_audit_entry`. "system" is a
  pseudo-role for the automated ACTIVE->EXPIRING->MATURED transitions
  Celery Beat will drive in Phase 7 against the sim clock.
- Shortfall checker (`app/rules/shortfall.py`) and penalty calculator
  (`app/rules/penalties.py`) are **fully config-driven**
  (`config/table_1_4.yaml`, `config/penalties.yaml`) rather than
  hard-coded, because the source blueprint itself flags the real Table 1.4
  amounts, the leased-campus multiplier, and the APH penalty rate
  (10%/20%/50%?) as **unresolved open questions for AICTE**
  (Blueprint.txt §17 item 1, §15 risk register) — not something to guess
  and ship as fact. Both config files carry an explicit placeholder
  warning; `calculate_penalty()` always returns `conflict_flagged: true`
  while the config says so, so the UI can show a banner instead of
  presenting a guessed rate as authoritative. Swapping in real AICTE
  figures later touches only these two YAML files.
- Release-eligibility checklist (`app/rules/release.py`): term-served,
  no-open-discrepancies, no-pending-scrutiny-observations, no-unpaid-
  penalties. The term-served rule cites "APH 2024-27, cl. 6.46" — the one
  citation the blueprint actually quotes (as the Compliance RAG agent's
  example format, line 371); the other three rules cite
  `"citation_pending"` rather than an invented clause number, since real
  clause sourcing is the Phase 6 Compliance RAG agent's job, not this
  checker's.
- Maker-checker (`assert_maker_checker`): approver must hold
  `competent_authority`, must not be the release requester, and must not
  be the scrutiny officer who handled that instrument's file (added
  `release_requests.scrutiny_officer_id` + `penalties.status` +
  `scrutiny_observations.status` columns via migration `f7dc9ddd76e3` to
  make these checks meaningful — they didn't exist after Phase 2).
- Tests: 52 new tests (58 total). Lifecycle tests are exhaustive, not
  spot-checks: every edge in `TRANSITIONS` is tested for its allowed
  role(s) *and* for rejection by every other role; every (from, to) pair
  **not** in the graph (>50 pairs) is asserted illegal in a single
  parametrized sweep — this is what "covers every transition" in the
  acceptance criterion actually required, not a handful of examples.

## 2026-10-23 (cont'd) — Phase 4

- **Deliberate reordering decision:** the brief's Phase 4 pipeline step
  "LLM gateway" belongs to Phase 6 (multi-provider, needs API keys this
  build doesn't have — the first real external-account dependency in the
  whole project). Rather than block Phase 4 on that, the extraction step
  is built behind a `FDRExtractor` protocol (`app/documents/extraction.py`)
  with `RegexFDRExtractor` as the Phase 4 stand-in — deterministic
  label:-value line matching, not an LLM call. Phase 6 adds
  `LLMGatewayExtractor` implementing the same interface; nothing else in
  the pipeline changes when that swap happens.
- **MinIO found archived again, mid-build:** `minio/minio` images are now
  fully pulled from Docker Hub (confirmed: `docker pull minio/minio:latest`
  and the previously-pinned release tag both now 404/"repository does not
  exist"). This happened *during* this session, after Phase 1 had already
  pinned a specific release tag — meaning even a pinned tag stopped being
  pullable. Already mitigated by the Phase 1 switch to Garage, which is
  unaffected; flagging because it's evidence the MinIO archival is an
  active, not just historical, risk — don't re-introduce it later.
- Full pipeline (`app/documents/`): `security_scan.py` (magic-byte
  detection via libmagic — rejects content/declared-type mismatches, e.g.
  a renamed script; **real** ClamAV scan via `clamd`, fail-closed if the
  scanner is unreachable — ran against the live `clamav/clamav:stable`
  container, not mocked), `hashing.py` (SHA-256 + perceptual hash via
  `imagehash`), `ocr.py` (real Tesseract OCR + `pdf2image` rasterisation,
  not PaddleOCR — chosen for container footprint on the 2 OCPU/12GB
  Oracle target), `redaction.py` (regex PII tokenise/rehydrate —
  Presidio-based version is Phase 6's job per the LLM gateway spec; same
  function signatures so the swap is drop-in), `extraction.py` (Pydantic
  schema + `RegexFDRExtractor`), `validation.py` (IFSC format, maturity =
  issue + tenor, amount-figures-vs-words, positive-amount), `forgery.py`
  (cross-institution duplicate instrument number — must run with
  bureau-side RLS context to see across institutions at all; duplicate
  pHash; suspicious PDF producer/creator metadata), `pipeline.py`
  (orchestrates all of the above, writes an audit entry per stage whether
  it passes or fails, and stores the sanitised file in **Garage**, not a
  mock — verified by reading the object back out).
  `confirm_extraction()` is a separate, explicit, role-gated
  (scrutiny_officer/verifier only) step — evidence_level only reaches L1
  on a human decision, never automatically from the pipeline, per "officer
  confirms (L1)" in the brief.
- **Encryption gap, not claimed as done:** the brief says "encrypted
  store"; this build writes to Garage over plain `put_object` with no
  server-side encryption configured. Garage does support SSE-C/age-based
  encryption, but wiring it up is deferred — tracked here rather than
  silently dropped.
- Synthetic FDR benchmark (`tests/test_extraction_accuracy.py` +
  `tests/fixtures.py`): 100 Faker-generated FDRs across exactly 8 layout
  templates (reportlab-rendered), run through real OCR + extraction.
  **Measured: 98.7% overall field accuracy (691/700)**, clearing the
  brief's >=95% target — but see the caveat in that test file's docstring:
  this is clean synthetic text via a deterministic regex extractor, not
  real scanned documents (AICTE hasn't supplied samples — Blueprint.txt
  §17 item 2) via the real LLM extractor. Found and fixed one real bug
  surfaced by this benchmark: `tests/fixtures.py`'s amount-words generator
  initially emitted digit counts ("Rupees 5 Lakh Only") while
  `validation.py`'s word-number parser expects spelled-out words ("Five
  Lakh") — caught by a failing pipeline-integration test, not assumed
  correct.
- Added `clamav` (clamav/clamav:stable) to Compose, `GARAGE_BUCKET`/
  `CLAMAV_HOST`/`CLAMAV_PORT` env wiring, and system packages

## 2026-10-23 (cont'd) — Phase 5

- Mock bank-confirmation API (`app/verification/mock_bank_api.py`): signed
  (HMAC) responses with simulated latency and a configurable failure
  rate. Every response carries `"simulated": True`; signature verified in
  tests, including a tamper-detection check. Mock SFMS/NeSL feed
  (`mock_sfms_feed.py`) for BG/E_BG/SURETY_BOND status, same
  `simulated: True` labelling. Neither touches a real bank system
  anywhere — both are explicitly SIMULATED per your instructions.
- **Hard rule enforced structurally, not just documented:** "the evidence
  level is never raised by AI; only human actions with uploaded evidence
  move L1->L2->L3" (Blueprint.txt line 381). `request_bank_confirmation`
  and `record_ledger_match` only ever write a `VerificationRecord`
  (evidence) — neither touches `instrument.evidence_level`. Only
  `confirm_bank_verification` (requires `verifier` role + a non-empty
  reason + an actually-uploaded `Document` as evidence) and
  `confirm_ledger_reconciliation` (requires `verifier` role + a
  verification record sourced specifically from the AICTE CSV) move
  evidence_level, and both write an audit entry. Tested: wrong role
  rejected, missing evidence rejected, missing reason rejected, wrong
  verification-record source rejected.
- **Real (non-simulated) part:** AICTE bank-statement CSV import +
  UTR/amount auto-match (`bank_statement.py`) for ONLINE_SD instruments —
  exact UTR+amount match, fuzzy narration+amount fallback when no UTR was
  recorded, explicit no-match. Added `instruments.utr` column (migration
  `ef43e7d9fd11`) since no column existed to match against.
- Declared-vs-confirmed diff (`diff.py`) and evidence-level badge metadata
  (`badges.py`, L0-L3 with label+icon+tone — colour-blind-safe per the
  design spec, never colour-only) are the API-shaped contracts the Phase
  9 web UI will render; no UI exists yet to consume them.
- **Found and fixed a real test-isolation bug, not a detector bug:** a
  pipeline-integration test failed on a pHash "duplicate" flag. Traced it
  to accumulated documents from earlier manual test runs during this
  session (4 total rows, 2 colliding pairs) — confirmed by truncating and
  re-running on a clean DB, where it passed. Root cause wasn't pHash
  being unreliable; it was that `tests/` had no session-level DB reset,
  so every local `pytest` invocation during development silently
  accumulated rows that later tests' assertions didn't account for. Fixed
  properly (not just patched around) with an autouse,
  session-scoped `conftest.py` fixture that truncates every table these
  tests write to once per session, run via the superuser role since
  `fdr_app` has no TRUNCATE grant. Verified by running the full suite
  twice in a row with no failures.
- Tests: 22 new (102 fast + the 100-doc benchmark).
